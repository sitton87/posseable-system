תרשים מפורט לפי שלבים

חיבור בין התיעוד, שכבות השירות, ה-API והמסכים בפועל. כל תרשים ממוקד בשאלה אחרת: מה דרוש להקמה, מי מטפל בהרשאות, ואיך הנתונים מגיעים עד למסך.

חזרה למפת העל

שלב 1 – תיעוד והקמה

קבצי מפתח: README, SETUP_GUIDE, database_schema.sql

עוד לפני שנוגעים בקוד, עוברים על המסמכים הראשיים ומוודאים שה-DB וה-ENV תואמים לדרישות. כך מבטיחים שכל שאר השלבים יתבססו על סביבה יציבה.

flowchart LR Docs[(README / SETUP_GUIDE)] --> Env[.env.local\nDB credentials] Env --> Schema[database_schema.sql] Schema --> SQL[(SQL Server)] Env --> Install[npm install] Install --> DevServer[npm run dev] DevServer --> Ready[מערכת מוכנה לבדיקה]

שלב 2 – תשתיות ושירותים

lib/, db/, middleware, hooks

שכבת התשתיות מספקת שירותים רוחביים: התחברות למסד הנתונים, הרשאות, שליחת אימיילים, יצירת סיסמאות ועוד. זוהי הליבה של ה-domain logic.

flowchart TD subgraph Backend DBConn[db/connection.ts\nquery()] Services[lib/services/*] AccessCtrl[lib/server/accessControl.ts] Utils[lib/utils/*] end Middleware[middleware.ts] --> AccessCtrl AccessCtrl --> Services Services --> DBConn DBConn --> SQL[(SQL Server)] Utils --> Services Services --> Hooks[app/hooks/usePagePermission] Hooks --> UI
  • `lib/services/authService.ts` – גישה לטבלת `app_user`
  • `lib/services/systemUserService.ts` – Role groups והרשאות
  • `lib/services/emailService.ts` – חיבור Gmail OAuth
  • `lib/utils/password.ts` – סיסמה זמנית עם prefix `PoS_`

שלב 3 – API וזרימת נתונים

app/api/** → lib/services → SQL

כל מודול עסקי מקבל סט ראוטים קבוע (GET, POST add, PUT update, DELETE). ה-Route Handlers מחברים את ה-HTTP לשירותים שבודקים הרשאות ומריצים שאילתות.

sequenceDiagram participant Client as דפדפן / fetch participant Route as Route Handler\napp/api/.../route.ts participant AccessCtrl as Access control participant Service as Service Layer\nlib/services/* participant DB as SQL Server Client->>Route: בקשת HTTP (GET/POST/PUT/DELETE) Route->>AccessCtrl: ensurePermissionResponse() Route->>Service: לוגיקה עסקית Service->>DB: query(sql, params) DB-->>Service: recordset Service-->>Route: Normalized data Route-->>Client: JSON response

דוגמה: `/api/equipment` → `app/api/equipment/route.ts` → קריאה ל-`query` דרך שירות מותאם → חזרה לטבלה ב-`app/(main)/equipment/page.tsx`.

שלב 4 – UI, Layout והרשאות

app/(main)/**/* + components

כאן הדפדפן מציג את הכל: Main layout עוטף את כל העמודים ב-Navbar ובגייט הרשאות. ה-Narbar משתמש ב-`usePermissions` כדי להסתיר קישורים שאין אליהם גישה, וה-PagePermissionGate מגן על התוכן עצמו.

flowchart LR RootLayout[app/layout.tsx\n] --> MainLayout[app/(main)/layout.tsx] MainLayout --> Navbar[Navbar.tsx] MainLayout --> Gate[PagePermissionGate] Gate --> Page[עמוד CRUD (equipment/donors...)] Navbar --> usePerm[usePermissions hook] usePerm --> APIperm[/api/auth/permissions] Page --> APIModule[/api/{module}/*]
  • `app/components/Navbar.tsx` – קישורים + פאנל משתמש + pin
  • `app/components/PagePermissionGate.tsx` – טוען הרשאות לפני render
  • `app/components/AccessDenied.tsx` – מסך fallback
  • `app/(main)/.../page.tsx` – כל מודול מציג טבלאות, מודלים וגרפים

חיבור ההרשאות מקצה לקצה

Session cookie → Permissions API → UI
flowchart TD Login[/api/auth/login/] --> SessionCookie[(session)] SessionCookie --> Middleware Middleware --> AppPages[PagePermissionGate] AppPages --> PermissionsAPI[/api/auth/permissions] PermissionsAPI --> SystemService[fetchPermissionsForRoleGroup] SystemService --> DBPerm[(app_role_group_permission)] PermissionsAPI --> UIHook[usePermissions] UIHook --> Navbar UIHook --> PageComponents

כך מבטיחים שכל פעולה – גם ב-UI וגם ב-API – תיבדק מול אותה שכבת הרשאה ותהיה עקבית עבור כל גולש.
